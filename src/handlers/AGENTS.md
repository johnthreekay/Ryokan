# handlers/AGENTS.md

Axum route handlers: what each module does, and the rules that apply on the handler side of the app. Loads with any file under `src/handlers/`. Auth has its own deeper file, `src/handlers/auth/AGENTS.md`. The route groups and their auth layers are in the root `AGENTS.md` ("Routes"), since they are wired in `main.rs`.

Keep this file under 40,000 characters (`wc -m`): past that, a Claude Code session with a 200K context window is given only its start. `tests/agents_md_audit.rs` enforces it.

## Modules

- **`handlers/`** — Axum route handlers. Page/feature modules: `library`, `search`, `downloads`, `settings`, `system`, `auth`, `media`, `progress`, `grab` (interactive file-picker — `/api/grab/{preview,confirm,heartbeat,selection,cancel}`; the modal posts its tick state to `POST /api/grab/selection/{id}` (when the list arrives, after every change, on close, from `pagehide` via sendBeacon, and from the page-lifecycle `unmount` on a boosted navigation, which also stops the heartbeat so the row can expire) onto `pending_grabs.wanted_indices_json`, so the walkaway auto-commit (`grab_sweep::auto_commit_row`) commits the last selection the way Confirm would; only an unposted selection means every file, while a posted empty one is a cancel (the torrent is deleted when the preview added it, as the Cancel button does; the modal disables Confirm at zero ticked, and the Wanted preselect says so when every matching file looks like an extra); `grab_confirm` records a grab only for a selection the client took: no file in range is a 400 (the modal's disabled Confirm, enforced), and when the client rejects the wanted-file write or the resume the answer is 502 with nothing committed and the pending row kept, so the open picker can send Confirm again, the same two cases in which the walkaway sweep records nothing; only the unwanted-file write is best-effort (`GrabConfirmResult.file_priority_errors`). the search menu (`GET /wanted/search-menu`) computes its one series through `rows_for_series` (per-series queries: `local_metadata::aired_episode_count`, `episode_tags::get_for_series`, `monitoring::get_monitored_episode_numbers`), never the library-wide three; ## Conventions

- **`/series/{id}` and `/api/series/{id}/...` take the library (internal) id.** The resolver (`reconcile::resolve_series_request`) tries an id as internal first and then as an AniList id, so a link that carries an AniList id hits whatever series has that internal id once the library is big enough (Cowboy Bebop is AniList 1). Link a tracked series by `series_id`; a link to a series that may not be in the library (relation cards, `RelationCard.tracked == false`) carries its AniList id **plus `?by=anilist`**, which `series_detail` and `api_series_detail` honor through `SeriesIdKind`. The series page's auto-search calls do the same: an untracked page carries `data-id-kind="anilist"` and posts `&by=anilist` (`seriesIdKindParam` in `series_helpers.js`), which `AutoSearchQuery.by` carries into `auto_search_series` / `auto_search_episode` and their search task. Internal callers of those handlers (the Wanted search, `redownload::search_replacement`) pass the library id, never `series.anilist_id`.
- **Streaming bodies must survive a poll after the end.** The compression layer polls a response body once more after it returns `None` while it finishes its encoder; `futures::stream::unfold` panics on that, and the panic cut the backup download off mid-stream for every browser (curl sends no `Accept-Encoding`, so it never showed there). `handlers::system::backup::file_stream` is `.fuse()`d and has a test that polls past the end; build any new streaming body the same way. The layer's predicate also skips `application/gzip`, since re-encoding an archive only costs CPU.
- **Stored credentials for other systems are write-only** (`handlers::secret_field`). Download client passwords, indexer API keys, the Jellyfin key, the Discord webhook URL, the generic webhook URL (its card shows the origin only) and webhook header values never render into a page: the field is empty with `KEEP_PLACEHOLDER` (header values show as `********`), and `secret_field::resolve` turns the post into the stored value: blank keeps it, `CLEAR` (the Clear button, `data-clear-secret` in `settings.js`) empties it, anything else replaces it. Blank keeps the stored secret **only while the URL keeps its scheme, host and port** (`same_destination`), on Save and on Test alike (the Test endpoints take the row `id` for this), so an edited address can't be used to send a saved secret elsewhere. The webhook HMAC secret follows the same rule. A scheme-less address is read the way the clients send it: `http://` for a local address (`jellyfin::is_local_address`), `https://` otherwise. A failed lookup of the saved row refuses the save rather than reading as "nothing saved". The legacy single-slot client passwords in `config` are no longer posted and were blanked once (`legacy_client_passwords_cleared_v1`). Keys Ryokan issues itself (the Sonarr / Radarr shim keys, the autobrr key) stay visible: the user copies them into the other app.
- **Built-in Nyaa card** (Settings → Indexers, first card, no delete): Nyaa is rendered from the config row, not an `indexers` row. Its columns (`nyaa_enabled`; `rss_enabled` + `disable_nyaa_rss`, surfaced as one RSS toggle and written together; `allow_non_english`, surfaced as the Categories select; `nyaa_download_client_id`; `default_restrict_to_uploader`) are written only by `handlers::settings::indexers::settings_indexers_nyaa_save` under `CONFIG_WRITE_LOCK`, and every tab form preserves them from `existing_cfg`. `rss_master_enabled` is the General tab's RSS switch (every source); `rss_enabled` is Nyaa-only and the System → RSS pane shows the master. `nyaa_enabled = 0` empties `auto_search::nyaa_search_categories` (so no collector builds a Nyaa query and the indexer fan-out runs alone), turns off the SeaDex seed in `seadex_gates` (its picks are Nyaa torrents), and the feed through `rss::nyaa_rss_enabled`; the manual Search page is deliberately not gated. Nyaa off with zero indexers is `handlers::library::search_has_no_source`, which the auto-search toast reports the way the adult note does.

## API-key surfaces

- **Sonarr/Radarr shim auth**: `arr_auth::check_api_key` middleware accepts `X-Api-Key` header *or* `?apikey=` query (percent-encoded), constant-time compared via `subtle` against `config.sonarr_api_key` / `config.radarr_api_key`. Transient config-load failures return **503 + `Retry-After`** (not 500) so Seerr doesn't long-back-off the indexer. Sonarr at `/api/v3/...`; Radarr at `/radarr/api/v3/...` (Seerr only allows two Sonarr + two Radarr slots; both shims must coexist on one host/port). `aliased(&["/camelCase", "/lowercase"], handler)` collapses Seerr's case-variant doublings — don't redirect, some clients won't follow. Provider order is fixed AL-first then MAL — never honor user-facing source toggles for the shim. **`tvdbId` is always a TVDB id** (`sonarr_compat::helpers::shim_ids`): `series.tvdb_id` / `tvdb_season`, which `add_series` stores from Seerr's request (so a show the mappings lack, added by title search, still reports it), else `anibridge::resolve_tvdb`, else 0; the TMDB id goes in `tmdbId`. Seerr's Sonarr scan resolves every listed series by TVDB id and asks `GET /series?tvdbId=` (honored) before declining a request whose show it didn't see; with TMDB ids there every Seerr request was declined on the next scan (reproduced against a scratch Seerr). A TVDB id is never retried as a TMDB id. `add_series` stores the pair only on a row that has none (`series::set_tvdb_ids_if_unset`), never on an existing row its title-search fallback landed on, so a later request can't move a series to another season. Season 0 is TVDB's (and TMDB's) Specials; every show key in the mappings names its season. It is reported as 0 (Seerr ignores it), left out of `seasonCount`, and `anibridge::lookup_show` never answers a missing season with it. `add_series` reads a request that monitors season 0 alone as a request for the Specials (season 0 never outranks a real season), and an add that names no season resolves the show's regular seasons without them (`whole_show_entries`; a show the mappings file only under Specials still resolves): read as "no season", a Specials request added every entry of the show, monitored. **The Radarr shim's `tmdbId` is a TMDB movie id**, a separate numbering from TMDB's shows: lookup and add resolve it through `anibridge::lookup_by_tmdb_movie` (the mappings' `tmdb_movie:<id>` keys, lowest AniList id first), and every movie payload reports `anibridge::resolve_tmdb_movie_id` (0 for a series with no film mapping), never `resolve_tmdb_id`, which answers with a show id for the Sonarr side's `tmdbId`. The movie table is built only from a movie's own record or an entry's own (`anilist:` / `mal:`): a show season's record lists every special beside every film of the franchise, and pairing those would give one film's id to all of them. Read from the show table, a movie request found nothing (most films have no show twin) or added the unrelated series whose show id equaled it, and the list reported series under show ids that are other films' numbers. The `system_status` endpoint reports `AppState.start_time` (boot wall-clock) for the Seerr liveness pill. Searches the shims start (SeriesSearch, MoviesSearch, search on add) go through `library::search::queue_shim_search`: only for an id that is a series in the library (an unknown internal id would reach `auto_search_series` as an AniList id), one per series queued or running, at most 64 waiting, two at a time; a skipped or dropped request is an `AutoSearch` warn, at most one a minute. Wrong keys are throttled per client and per shim (`src/handlers/auth/AGENTS.md`).
- **Webhook auth**: `handlers::webhook::autobrr` accepts `X-Api-Key` header *or* `?apikey=` query, constant-time compared against `config.autobrr_api_key`. Empty configured key returns **503 + Retry-After** ("autobrr webhook is disabled") rather than treating empty-key match as success. Mismatch is 401. A push without `info_hash` takes it from the magnet's `btih`, or, for a torrent client only, from the `.torrent` itself (`services::torrent_file`: the SHA-1 of the top-level `info` dict, 10 MB cap, parsed under `spawn_blocking`); with no hash the grab could only be found by name, and a single-file torrent named after its file never matched. A misgrab's hash is checked once the series is matched (`grabbed_torrents::is_blocklisted_for`). The push's `indexer` (autobrr's identifier) is matched to an indexer row by name for its client pin and seed rules; with no match, `nyaa` / `nyaa.si` routes like a Nyaa grab (`client_for_nyaa_with_id`) and anything else goes to the torrent default with no seed rules, but only once it is known to be a torrent (an `info_hash`, a magnet, or a `torrent_url` whose body reads as a .torrent). Anything else is skipped (200) with a warn telling the user to give the Ryokan indexer autobrr's name: without the row there is no protocol, and a Usenet push's NZB link used to land in the torrent client with an empty hash. With no torrent client at all, a hashless unmatched push is skipped without a fetch rather than answering a 503 autobrr retries forever. Unmatched pushes used to be skipped, which dropped every Nyaa push since Nyaa is not an indexer row. Key rotation is a separate handler at `POST /settings/autobrr/regenerate-key` (`handlers/settings/autobrr_key.rs`) — distinct from the regular Settings save so an accidental tab POST can't silently rotate or wipe the key. Future webhook receivers (e.g. radarr companion) land as siblings under `handlers/webhook/` so the auth + body-shape pattern stays consistent.
